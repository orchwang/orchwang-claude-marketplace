# Reference: 온톨로지 모델링 1급 개념

온톨로지의 뼈대는 **객체 타입 · 속성 · 링크 타입**이다. 물리 테이블을 그대로 옮기지 않고, "세계의 의미"를 이 개념들로 재구성한다.

## 1. 객체 타입 (Object Type)

세계의 **명사** — 사람·주문·제품·설비·계좌처럼 도메인이 이야기하는 실체.

- **정의**: 이름(도메인 언어) + 속성 집합 + 기본키.
- **속성(Property)**: 객체의 특성. 타입(문자열·수·날짜·enum)·의미·표시명. **표시 속성(title property)**을 정해 사람이 객체를 식별하게 한다.
- **기본키(Primary Key)**: 객체 인스턴스를 유일하게 식별. 여러 백킹 데이터셋에서 같은 실체를 이어붙이는 기준이 된다(→ 엔티티 해소).
- **파생 속성**: 다른 속성/링크에서 계산되는 값(예: 주문 총액).

**설계 지침**
- 도메인 전문가가 쓰는 단어를 객체 이름으로. 물리 테이블명(`tbl_ord_hdr`)이 아니라 "주문".
- 하나의 물리 테이블이 여러 객체가 되거나, 여러 테이블이 하나의 객체가 될 수 있다(구조 ≠ 의미).
- 속성은 "이 객체를 보는 사람이 알고 싶은 것"만. 물리 컬럼을 전부 승격하지 않는다.

## 2. 링크 타입 (Link Type)

세계의 **동사/관계** — "고객이 주문을 한다", "주문이 제품을 포함한다". 온톨로지에서 관계는 **1급 개념**이다(속성 안에 외래키로 숨기지 않는다).

- **정의**: 두 객체 타입 사이의 이름 있는 관계 + 카디널리티 + 방향/역방향 이름.
- **카디널리티**: 1:1 / 1:N / N:M. N:M은 대개 백킹 조인 테이블(또는 링크 객체)로 실현.
- **탐색성(Navigability)**: 양방향 이름을 준다 — 고객→"주문한 주문들", 주문→"주문한 고객". 그래프 탐색·질의의 언어가 된다.
- **링크에 속성이 필요하면**: 관계 자체가 실체(예: "회원-역할" 배정에 시작일·권한)라면 **링크 객체(중간 객체 타입)**로 승격.

**설계 지침**
- 외래키를 발견하면 "이건 링크다"라고 읽는다. 조인 로직을 매번 재작성하는 대신 링크로 고정.
- 방향과 역방향 이름을 항상 도메인 언어로 짓는다.

## 3. 객체 그래프 (Object Graph)

객체(노드) + 링크(엣지)로 이루어진 그래프. 온톨로지의 런타임 형태다.

- **그래프 탐색**: "이 고객이 주문한 것 중 특정 제품을 포함한 주문" 같은 질의를 링크를 따라 표현.
- **관점 전환**: 같은 그래프를 고객 중심/제품 중심/설비 중심으로 볼 수 있다 — 물리 스키마 하나에 갇히지 않는 이유.

## 4. 물리 데이터 모델과의 관계

| 물리(데이터 모델) | 의미(온톨로지) |
|-------------------|----------------|
| 테이블 / 뷰 | 객체 타입(1:1 아님 — 재구성) |
| 컬럼 | 속성(선별) |
| 외래키 / 조인 | 링크 타입(1급) |
| PK | 객체 기본키(+ 엔티티 해소 기준) |
| 조인 쿼리 | 그래프 탐색 |

> 핵심: 온톨로지는 물리 모델 **위에** 놓인 의미 계층이다. 매핑(→ `mapping-and-actions.md`)이 둘을 잇는다.

## 5. 흔한 anti-pattern

- **스키마 승격**: 물리 테이블·컬럼을 1:1로 객체·속성으로 올림 → 의미가 아니라 저장 구조를 모델링하게 됨.
- **관계 은닉**: 관계를 외래키 속성으로만 두고 링크 타입을 안 만듦 → 탐색·재사용 불가.
- **표시 속성 부재**: 사람이 객체를 못 알아봄(ID만 노출).
- **과잉 속성**: 소비자가 안 쓰는 물리 컬럼까지 전부 노출.
