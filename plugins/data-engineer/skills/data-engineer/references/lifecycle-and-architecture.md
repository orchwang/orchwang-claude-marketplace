# Reference: 데이터 엔지니어링 수명주기 · 아키텍처

이 문서는 `data-engineer` skill/agent가 설계 판단을 내릴 때 여는 개념 지도다. 모든 요청을 **수명주기의 어느 칸**에 놓고, **저류(undercurrents)**를 함께 본 뒤, **아키텍처 패턴**을 고른다.

## 1. 데이터 엔지니어링 수명주기 (Data Engineering Lifecycle)

원천에서 소비자까지의 흐름을 5단계로 본다. 모든 도구·기술은 이 중 한 칸에 들어간다.

```
생성(Generation) → 수집(Ingestion) → 저장(Storage) → 변환(Transformation) → 서빙(Serving)
```

| 단계 | 책임 | 핵심 질문 |
|------|------|----------|
| 생성 Generation | 원천 시스템(앱 DB·이벤트·API·SaaS) | 우리가 통제 못 하는 스키마·품질을 어떻게 다루나 |
| 수집 Ingestion | 원천→플랫폼으로 데이터를 들여옴 | 배치 vs 스트리밍? push vs pull? CDC? 스키마 진화? |
| 저장 Storage | 들여온 데이터를 안전·경제적으로 보관 | 파일 포맷·테이블 포맷·파티셔닝·수명주기 |
| 변환 Transformation | 원본을 쓸 수 있는 형태로 다듬음 | 어디서 변환(ELT)? 모델링? 증분? 멱등? |
| 서빙 Serving | 분석·ML·역ETL로 가치 전달 | 소비자는 누구(BI·ML·앱)? 신선도 SLA? |

**설계 원칙**: 요청을 받으면 먼저 "이건 수집/저장/변환/서빙 중 무엇인가"를 확정한다. 대부분의 모호함은 단계 경계에서 생긴다.

## 2. 저류 (Undercurrents) — 모든 단계를 관통하는 관심사

수명주기의 각 칸을 세로로 꿰뚫는 6가지. 설계할 때 항상 함께 본다.

- **보안(Security)**: 최소 권한, 암호화(전송·저장), PII 취급.
- **데이터 관리(Data Management)**: 카탈로그, 리니지, 마스터/참조 데이터, 수명주기.
- **DataOps**: 자동화·관측가능성·인시던트 대응(CI/CD·모니터링·SLA).
- **데이터 아키텍처**: 시스템 전체의 구조·트레이드오프 결정.
- **오케스트레이션(Orchestration)**: 의존성·스케줄·재시도·백필.
- **소프트웨어 엔지니어링**: 테스트·버전관리·모듈화·코드 품질.

## 3. 역사적 전환 — "왜 지금 이 도구인가"

- **ETL → ELT**: 스토리지·컴퓨팅이 싸지면서 "먼저 적재하고 나중에 변환". 변환을 웨어하우스/레이크 안에서(dbt·SQL) 수행.
- **DW → Data Lake → Lakehouse**: 정형 중심 웨어하우스 → 원본 보존 레이크(스키마-온-리드) → 둘을 통합한 레이크하우스(열지향 파일 + 개방형 테이블 포맷 + ACID).
- **배치 → 스트리밍**: Hadoop/MapReduce → Spark(인메모리) → 실시간(Kafka·Flink)과 Modern Data Stack.

> 도구 선택을 물으면, 그 도구가 **어떤 한계를 풀려고 등장했는지**로 근거를 댄다.

## 4. 아키텍처 패턴 — 언제 무엇을

### 4.1 순수 배치 (Batch)
- 주기적(시간/일 단위) 처리. 단순·저비용·재처리 쉬움.
- **선택 기준**: 신선도 요구가 분~일 단위, 대부분의 분석/리포팅.

### 4.2 Lambda
- **배치 레이어**(정확·느림) + **스피드 레이어**(근사·빠름) + 서빙 레이어에서 병합.
- 장점: 실시간성 + 재처리 정확성. 단점: **로직 이중 구현**(배치/스트림 코드 중복) → 유지비.
- **선택 기준**: 실시간 대시보드가 필요하지만 최종 정확성도 배치로 보정해야 할 때.

### 4.3 Kappa
- 스트림 하나로 통합. 모든 데이터를 **불변 로그(Kafka)**로 보고, 재처리는 로그 리플레이.
- 장점: 단일 코드베이스. 단점: 대규모 과거 재처리·스트림 상태 관리 난이도.
- **선택 기준**: 이벤트 중심, 로직을 한 벌로 유지하고 싶을 때.

### 4.4 Medallion (Bronze / Silver / Gold)
- **Bronze**: 원본 그대로 적재(감사·재처리 원천). **Silver**: 정제·표준화·조인. **Gold**: 비즈니스 집계·마트.
- 레이크하우스에서 사실상 표준 계층화. dbt 모델 계층(staging→intermediate→marts)과 자연스럽게 대응.
- **선택 기준**: 레이크하우스 기반 대부분의 배치/증분 파이프라인의 기본 골격.

### 패턴 선택 요약

| 신선도 요구 | 재처리 필요성 | 권장 |
|------------|--------------|------|
| 분~일 | 높음 | Batch + Medallion |
| 초~분 + 배치 보정 | 높음 | Lambda |
| 초~분, 단일 로직 | 로그 리플레이 | Kappa |

## 5. 배치 vs 스트리밍 판단 축

- **지연시간(latency)**: 초 이하가 진짜 필요한가, 아니면 "실시간처럼 보이는 마이크로배치"로 충분한가.
- **정확성/일관성**: 정확히 한 번(exactly-once)이 필요한가, 근사로 충분한가.
- **순서·상태**: 이벤트 순서·윈도우·조인 상태가 있는가.
- **비용**: 상시 가동 스트림 인프라 vs 주기적 배치 컴퓨트.

> 실무 기본값: **명확한 실시간 요구가 없으면 배치(또는 마이크로배치)로 시작**하고, 필요할 때 스트리밍으로 승격한다.
