## 1. 왜 그래프인가 — 저장소 선택의 첫 관문

### 1.1 핵심 개념

- **지식 그래프 = 노드·관계로 표현한 사실의 망.** 최소 구조는 셋뿐이다.
  - **노드(node)**: 세상의 개체(사람·회사·제품·사건·유전자).
  - **엣지(edge)**: 방향 있는 관계(`근무`, `출시`, `상호작용`).
  - **속성(property)**: 노드·엣지에 붙는 값(사람의 `이름`, 관계의 `시작일`).
- 각 화살표 하나가 **트리플**(주어–술어–목적어)이고, 트리플을 쌓으면 자연스럽게 하나의 연결망으로 자란다.
- **핵심 전환: "관계를 계산하지 말고 저장하라."**
  - 관계형은 관계를 외래키 **조인으로 질의 시점에 계산**한다.
  - 그래프는 관계 자체를 **물리적 포인터로 저장**한다(index-free adjacency). 이웃 이동에 조인이 필요 없어 **다중 홉(multi-hop)** 탐색이 값싸다.
- 세 저장소는 경쟁이 아니라 **상보적**이며, **질문의 성질이 렌즈를 고른다.**

### 1.2 의사결정 규칙

| 질문의 성질 | 예시 | 택할 저장소 |
| --- | --- | --- |
| 정형 집계·트랜잭션 | "이 고객의 이번 달 총 주문액은?" | **관계형 DB** |
| 의미 유사도 검색 | "이 문장과 비슷한 문단은?" | **벡터 DB** |
| 연결·경로·다중 홉 | "3다리 건너 연결된 계좌는?" | **지식 그래프** |
| 전역(global) 요약 | "코퍼스 전체를 관통하는 리스크는?" | **그래프**(+벡터 하이브리드) |
| 설명가능한 근거 필요 | "왜 이 답인가 — 경로로 제시" | **그래프** |

- **다중 홉이거나 홉 수가 미리 정해지지 않은 질문**("연결이 끊길 때까지")이면 그래프를 택한다.
- **답이 한 조각에 없고 여러 사실을 이어야** 나오면 그래프(또는 벡터→그래프 하이브리드)를 택한다.
- **순수 유사도 검색·대량 정형 집계**만이면 그래프를 택하지 않는다(각각 벡터·관계형이 낫다).

### 1.3 도구·문법 스니펫

같은 "3다리 건너 연결" 질문을 두 방식으로 비교한다.

```sql
-- 관계형: 홉마다 self-join → 중간 결과 ×N → ×N² → ×N³ (조인 폭발)
SELECT DISTINCT p3.name
FROM   people p0
JOIN   transfers t1 ON t1.from_id = p0.id
JOIN   people p1     ON p1.id = t1.to_id
JOIN   transfers t2 ON t2.from_id = p1.id
JOIN   people p2     ON p2.id = t2.to_id
JOIN   transfers t3 ON t3.from_id = p2.id
JOIN   people p3     ON p3.id = t3.to_id
WHERE  p0.name = '김지수' AND p3.id <> p0.id;
```

```cypher
// 그래프: 가변 길이 경로 *1..3 — 홉 수를 데이터가 정하게 둔다
MATCH (me:Person {name: '김지수'})-[:TRANSFER*1..3]->(other:Person)
WHERE other <> me
RETURN DISTINCT other.name;
```

### 1.4 흔한 함정

- **그래프가 관계형을 대체한다는 오해.** 원장·재무·재고 같은 정형 트랜잭션은 여전히 관계형이 정답이다. 그래프는 *관계 자체가 1급 질문*이 되는 워크로드용이다.
- **벡터 RAG로 다중 홉을 풀려는 시도.** 벡터는 비슷한 조각을 top-k로 모을 뿐, 흩어진 사실을 **스스로 잇지 못한다.** 전역 질문·설명가능성에도 약하다.
- **저장소를 먼저 정하고 질문을 맞추기.** 순서가 거꾸로다 — 질문의 성질이 저장소를 정한다.

## 2. 그래프 저장·질의 — 속성 그래프(Cypher) vs RDF(SPARQL)

### 2.1 핵심 개념

그래프를 다루는 두 계열이 있고, 서로 다른 우선순위를 앞세운다.

- **속성 그래프(labeled property graph)** — 실무 주류(Neo4j 대표). **저장·탐색의 실용성**.
  - 노드: **라벨**로 종류 표시(`:Customer`) + **속성** 내장(`{name:"김지수"}`).
  - 엣지: **타입**(`:PLACED`) + **엣지 자신도 속성**을 가짐(`{placedAt: ...}`).
  - 질의어: **Cypher / GQL** — 화살표 ASCII로 그래프 모양을 그대로 적는다.
- **RDF 트리플** — 시맨틱 웹 계보. **표준·의미론·추론**.
  - 모든 사실을 **주어–술어–목적어 트리플**로 쪼개고, 모든 리소스·술어를 **URI로 전역 식별**.
  - `이름`조차 별도 트리플. 스키마도 데이터.
  - 질의어: **SPARQL** — 변수를 품은 트리플 패턴을 매칭.
- 두 질의어의 발상은 **형제**다 — "질의가 모델을 닮는다"(변수를 품은 관계 패턴을 그래프에 매칭). 차이는 **표현 단위**(화살표 vs 트리플)와 그 위에 얹히는 **OWL 추론**의 유무.

### 2.2 의사결정 규칙

| 조건 | 택할 모델 |
| --- | --- |
| 내 앱의 그래프를 빠르게 짓고 깊게 탐색 | **속성 그래프** |
| 추천·사기 탐지·운영 앱·개발자 경험 중시 | **속성 그래프** |
| 엣지에 속성을 직접 달아야 함 | **속성 그래프**(RDF는 reification 필요) |
| 여러 기관·출처를 표준 어휘로 통합·연합 | **RDF** |
| OWL 논리 추론이 요건 | **RDF** |
| 공개 온톨로지·linked data(의료·정부·도서관) | **RDF** |
| LLM 기반 구축(4단계 이후) 실무 예제 | 대개 **속성 그래프(Neo4j)** |

- **거친 요약**: "내 애플리케이션 그래프를 빠르게 짓고 탐색"이면 속성 그래프, "여러 출처를 표준 어휘로 통합·추론"이면 RDF.
- 신규 프로젝트 다수는 **속성 그래프에서 출발**한다.

### 2.3 도구·문법 스니펫

**Cypher — 생성·패턴 매칭·가변 길이 경로**

```cypher
// 생성 — 라벨·속성 내장, 엣지에도 속성
CREATE (c:Customer {id:"C-042", name:"김지수", tier:"VIP"})
CREATE (o:Order {id:"O-1001", amount:1200000})
CREATE (c)-[:PLACED {placedAt: date("2026-07-13")}]->(o);

// 패턴 매칭 — 질의가 화살표 그림을 닮는다
MATCH (c:Customer)-[:PLACED]->(o:Order)-[:CONTAINS]->(p:Product {name:"노트북"})
RETURN c.name, o.amount ORDER BY o.amount DESC;

// 가변 길이 경로 — 홉 수를 데이터가 정한다
MATCH path = (a:Account {flagged:true})-[:TRANSFER*1..4]->(b:Account)
RETURN path LIMIT 20;

// 최단 경로
MATCH p = shortestPath((x:Person {name:"김지수"})-[:KNOWS*]-(y:Person {name:"이서준"}))
RETURN p;
```

**무결성 제약(속성 그래프는 schema-optional)**

```cypher
CREATE CONSTRAINT customer_id_unique IF NOT EXISTS
FOR (c:Customer) REQUIRE c.id IS UNIQUE;               // 유일성(기본키 역할)

CREATE CONSTRAINT order_amount_exists IF NOT EXISTS
FOR (o:Order) REQUIRE o.amount IS NOT NULL;            // 존재성(필수 속성)
```

**RDF/Turtle 저장 + SPARQL 질의**

```turtle
@prefix ex: <http://example.org/ontology#> .
c:C-042  a ex:Customer ;      # "a" = rdf:type
         ex:name   "김지수" ;
         ex:placed o:O-1001 .
o:O-1001 a ex:Order ; ex:contains ex:P-77 .
```

```sparql
PREFIX ex: <http://example.org/ontology#>
SELECT ?customerName
WHERE {
  ?customer ex:name   ?customerName ;
            ex:placed ?order .
  ?order    ex:contains ?product .
  ?product  ex:name     "노트북" .
}
```

동일 관계의 문법 대응:

| 관계 | Cypher | SPARQL |
| --- | --- | --- |
| 고객→주문 | `(c)-[:PLACED]->(o)` | `?c ex:placed ?o .` |
| 주문→제품 | `(o)-[:CONTAINS]->(p)` | `?o ex:contains ?p .` |
| 제품 이름 | `(p {name:"노트북"})` | `?p ex:name "노트북" .` |

### 2.4 지형도 (좌표만)

- **속성 그래프 DB**: Neo4j(사실상 표준), Memgraph(인메모리·실시간), TigerGraph(대규모 분석), Amazon Neptune(관리형, 속성 그래프+RDF).
- **트리플스토어(RDF)**: Ontotext GraphDB, Blazegraph, Amazon Neptune, Apache Jena.
- **질의어**: Cypher/GQL(속성 그래프), SPARQL(RDF), Gremlin(TinkerPop, 다중 DB).
- **GQL 표준**: 2024년 ISO가 GQL을 SQL에 이은 두 번째 ISO 표준 DB 언어로 제정 — Cypher 계열 문법 표준화, 그래프 질의도 이식 가능한 표준을 갖기 시작.

### 2.5 흔한 함정

- **RDF에서 엣지에 값을 직접 달려다 막힘.** 관계에 속성을 달려면 관계를 노드로 승격하는 **reification**이 필요하고 표현이 장황해진다.
- **RDF의 균질성 과소평가/과대평가.** 힘: 같은 URI는 같은 실체로 자동 병합(데이터 연합). 값: 같은 사실에 트리플 수가 많아짐.
- **가변 길이 경로를 SQL로 옮기려는 시도.** `*1..n`, `shortestPath(...)`는 관계형으로 옮기기 지극히 어렵거나 불가능하다.
- **속성 그래프의 schema-optional을 무규율로 방치.** 최소 제약(유일성·존재성)조차 걸지 않으면 라벨·속성이 난립한다.

## 3. 전통 구축 파이프라인 — 텍스트를 그래프로

### 3.1 핵심 개념

그래프 DB는 **빈 그릇**이다. 채우는 일은 4관문의 **반복적(iterative) 파이프라인**이다.

```
비정형 텍스트 → ① NER → ② RE → ③ 스키마 설계 → ④ 엔티티 해소 → 지식 그래프
                 ▲ 스키마가 추출을 안내          │
                 └────── 해소가 품질 문제 발견 → 재추출 ┘
```

- **① 개체명 인식(NER)**: 텍스트에서 개체를 찾아 종류를 붙임 → **노드 후보**.
  - "김지수는 2021년 누리테크에 합류" → `[김지수]사람 [2021년]날짜 [누리테크]회사`.
- **② 관계 추출(RE)**: 개체 쌍 사이 관계를 뽑음 → **엣지**. NER(노드)+RE(엣지)가 트리플을 완성.
  - `(김지수)-[근무]->(누리테크)`, `(김지수)-[합류시점]->(2021년)`.
- **③ 스키마·온톨로지 설계**: 담을 타입·관계를 미리 정의 → 추출이 얹힐 **뼈대**. 사실상 도메인 모델링("무엇을 노드로, 무엇을 속성으로, 무엇을 관계로 승격"). **이 단계는 ontology-expert 플러그인의 전문 영역과 정확히 맞물린다 — 시맨틱 레이어 설계가 필요하면 위임한다.**
- **④ 엔티티 해소**: 여러 소스에 흩어진 **같은 실체를 하나의 노드로 병합**. 가장 지저분하고 결정적.

### 3.2 의사결정 규칙

**추출 방법 선택(전통)**

| 상황 | 방법 | 주의 |
| --- | --- | --- |
| 좁고 안정적인 패턴 | 규칙 기반 | 표현 변주에 취약, 규칙 폭발 |
| 라벨 코퍼스 확보됨 | 통계·지도학습(CRF·신경망) | 도메인마다 대량 라벨링 |
| 알려진 개체 목록 존재 | 사전·gazetteer 매칭 | 신조어·새 개체에 약함 |

- **도메인이 바뀌면 전통 추출기는 처음부터 다시**다(낮은 이식성). 이 비용이 LLM 추출로 판이 뒤집히는 배경 — 단, **스키마 규율과 엔티티 해소 숙제는 LLM도 지우지 못한다.**

**스키마 전략 선택**

| 조건 | 전략 |
| --- | --- |
| 일관성·품질·규제 도메인, 안정된 타입 | **스키마-우선(schema-first)** — 정의에 맞는 것만 수용 |
| 새 도메인·탐색적 구축, 진화하는 타입 | **스키마-유연(schema-flexible)** — 넓게 받고 점진적으로 조임 |

- RDF/OWL·규제 도메인은 schema-first에, 속성 그래프·LLM 기반 구축은 schema-flexible에 가깝다.

**엔티티 해소 오류의 비대칭**

- **false merge**(다른 둘을 합침) → 무관한 사실이 한 노드에 오염 → 그래프 신뢰 붕괴.
- **false split**(같은 하나를 못 합침) → 연결 끊김 → 다중 홉 질의 실패.
- 규제·의료처럼 오류가 곧 위반·사고가 되는 영역이면 **완전 자동화보다 사람 검수(휴먼인더루프)**를 남기는 것이 표준.

### 3.3 도구·문법 스니펫

**NER + RE 출력 형태**

```text
입력:  "김지수는 2021년 누리테크에 합류해 미리내 개발을 이끌었다."
NER:   [김지수]사람  [2021년]날짜  [누리테크]회사  [미리내]제품
RE:    (김지수)-[근무]->(누리테크)
       (김지수)-[합류시점]->(2021년)
       (누리테크)-[개발]->(미리내)
       (김지수)-[주도]->(미리내)
```

**엔티티 해소 3단계 깔때기**

```
모든 쌍 O(n²) — 감당 불가
   │
   ├─ ① 블로킹(blocking):   후보 쌍만 남김 (같은 도메인·지역끼리)
   ├─ ② 매칭(matching):     유사도 계산 (Jaro-Winkler, 속성 일치, 학습 분류기)
   │        └─ 애매한 쌍 → 사람 검수(휴먼인더루프) → 군집으로 복귀
   └─ ③ 군집·병합(clustering): 같은 실체로 묶고 대표 노드 통합 (+신뢰도 보존)
```

### 3.4 흔한 함정

- **추출 트리플을 스키마 없이 그냥 쌓기** → 일관성 없는 잡동사니, 질의 예측 불가.
- **전통 추출기를 다른 도메인에 재사용** → 의료용 튜닝 추출기는 금융 리포트에 못 쓴다. 새 관계 유형마다 라벨링·재학습.
- **엔티티 해소를 후순위로 미룸** → 가장 어렵고 가장 결정적. false merge/split 균형이 그래프 신뢰를 정한다.
- **신뢰도(confidence)를 버림** → 병합 결과에 근거가 없으면 사후 검수·롤백이 불가능하다.
- **O(n²) 전수 비교를 그대로 시도** → 블로킹 없이는 현실 규모에서 불가능.
- **LLM이 스키마·해소까지 대체한다는 기대** → LLM은 추출 문턱을 낮출 뿐, 스키마 규율·엔티티 해소가 오히려 품질을 가른다.

## 부록 — 저장소 3렌즈 요약표

| 렌즈 | 저장하는 것 | 잘 답하는 질문 | 약한 지점 |
| --- | --- | --- | --- |
| 관계형 DB | 행·열, 관계는 외래키 | 정형 집계·트랜잭션 | 깊은 다중 홉(조인 폭발) |
| 벡터 DB | 의미 임베딩 | 의미 유사 검색·벡터 RAG | 연결·전역·설명가능성 |
