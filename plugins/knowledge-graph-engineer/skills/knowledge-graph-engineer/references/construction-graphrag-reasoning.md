## 1. LLM 기반 그래프 구축

### 1.1 핵심 개념

- **전환의 요지**: 규칙·통계·지도학습 파이프라인(도메인마다 라벨링·튜닝 비용 큼, 이식성 낮음) 대신, **LLM에 스키마를 프롬프트로 알려 주고 문서에서 트리플을 뽑게** 함. 도메인 변경 = 프롬프트 스키마 교체, 재학습 없음.
- **파이프라인은 사라지지 않음**: LLM은 파이프라인의 "추출" 상자 하나를 바꿀 뿐. 앞의 스키마 안내와 뒤의 검증은 그대로.
  - 흐름: `문서 → 청킹 → (스키마 + LLM 추출) → 후보 트리플 → 검증 → 엔티티 해소 → KG`, 검증 실패 시 재추출/사람 검수로 루프백.
- **스키마 유도 추출(schema-guided)**: 허용 노드 타입·관계 타입을 프롬프트에 실어, LLM이 그 어휘 안에서만 추출하게 함 → 일관성 급상승.
- **구조화 출력(structured output)**: JSON 스키마 / 함수 호출(tool calling)로 출력 형식 강제 → 후처리 파싱 안정.
- **추출 ≠ 추론**: "텍스트에 없는 사실은 추론하지 마라"로 추출 단계와 6단계 추론을 분리. 환각 억제의 핵심 가드레일.

### 1.2 의사결정 규칙

| 상황 | 선택 |
| --- | --- |
| 도메인이 자주 바뀌거나 라벨링 코퍼스가 없음 | **LLM 추출** (프롬프트 스키마 교체로 적응) |
| 관계 타입이 고정·대량·저지연·저비용 필요 | **전통 파이프라인** (학습형 추출기) |
| 경계 사례(대명사·암시 관계) 품질 필요 | LLM + **few-shot 예시 1~2개** |
| 안전·규제가 걸린 관계(의료·금융) | LLM 대량 추출 + **도메인 전문가 검수 확정** |
| 출력 파싱이 자주 깨짐 | JSON 스키마 / 함수 호출로 **구조화 출력 강제** |
| 같은 개체가 여러 표기로 등장 | 추출 후 **엔티티 해소(병합)** 필수 |

### 1.3 도구·스니펫

- **LangChain `LLMGraphTransformer`**: 문서 → `GraphDocument`(노드·관계), `Neo4jGraph`로 바로 적재. 허용 타입 파라미터로 스키마 제약.
- **LlamaIndex Property Graph Index**: 구축 + 검색을 하나로 묶음. `SchemaLLMPathExtractor` 등으로 제약, 구축 그래프를 GraphRAG 검색에 그대로 연결.

```python
# LangChain — 스키마로 제약한 LLM 추출
from langchain_experimental.graph_transformers import LLMGraphTransformer

transformer = LLMGraphTransformer(
    llm=llm,
    allowed_nodes=["사람", "회사", "제품", "날짜"],
    allowed_relationships=["근무", "출시", "합류시점"],
    strict_mode=True,          # 스키마 밖 타입 배제 → 일관성
)
graph_docs = transformer.convert_to_graph_documents(documents)
neo4j_graph.add_graph_documents(graph_docs)
```

```text
[프롬프트 골격]
허용 노드 타입: 사람, 회사, 제품, 날짜
허용 관계 타입: 근무(사람→회사), 출시(회사→제품), 합류시점(사람→날짜)
스키마에 없는 타입·관계는 만들지 마라. 텍스트에 없는 사실은 추론하지 마라.
각 트리플에 출처 근거(source span)를 함께 출력하라.
출력은 JSON 스키마(nodes[], edges[])를 따른다.
```

### 1.4 함정·비용

- **환각**: 원문에 없는 관계를 지어냄. 방어 = 추론 금지 가드레일 + **출처 근거(source span) 원문 대조** + 저신뢰 트리플 보류.
- **불일치**: 같은 개체 다중 표기("누리테크"/"Nuritech"/"㈜누리테크"). LLM이 등장해도 **엔티티 해소는 사라지지 않고 오히려 더 자주 필요**.
- **스키마 위반·중복**: 허용 밖 타입, 방향 뒤집힌 관계, 중복 트리플. 스키마 검증기로 자동 거름 + 중복 병합.
- **청킹**: 한 사실이 청크 경계에서 잘리지 않게 분할(컨텍스트 창 고려).
- **비용**: 문서 전체를 LLM 통과 → 토큰 비용·지연 큼. 배치·캐싱·모델 선택으로 관리.
- **완전 자동화 불가**: 표준은 **휴먼인더루프**. 검증기가 대부분 거르고, 저신뢰·경계 트리플만 사람에게 → 판정을 프롬프트·규칙에 피드백.

## 2. GraphRAG

### 2.1 핵심 개념

- **벡터 RAG의 동작**: 질문과 의미가 가까운 조각(top-k)을 찾아 LLM에 넘김. **개체 간 명시적 구조가 없음** → 조각은 독립된 점.
- **GraphRAG = 벡터 RAG의 보완(대체 아님)**: 문서에서 지식 그래프를 짓고 **community detection**으로 주제 클러스터를 만들어 **요약을 미리 구움**.
- **두 단계**:
  - **인덱싱(한 번, 무겁게)**: `문서 → LLM 추출 → KG → community detection → 커뮤니티 요약`.
  - **쿼리(질문 크기에 따라)**: local vs global 두 갈래.
- **community detection**: 촘촘히 연결된 노드 묶음(주제 클러스터)을 찾음. **Leiden** 같은 알고리즘이 계층적 주제 그룹으로 분할.
- **local search**: 특정 개체 중심. 그 노드의 **이웃(연결 개체·관계) + 관련 원문 조각**을 모아 LLM에 넘김 → 다중 홉 질문 해결. 자체가 그래프+텍스트 하이브리드.
- **global search**: 코퍼스 전체 조망. 미리 구운 **커뮤니티 요약을 map-reduce**(각 요약이 부분 답변 → 종합).

### 2.2 의사결정 규칙

| 질문/조건 | 선택 |
| --- | --- |
| "X와 연결된 Y를 거쳐 Z…" 다중 홉, 특정 개체 중심 | **local search** |
| "코퍼스 전체의 핵심 리스크 5가지?" 전역 종합 | **global search** |
| 단순 의미 유사 Q&A, 최신성 절대적 | **벡터 RAG** (더 싸고 빠름) |
| 연결·종합이 답이고 코퍼스가 상대적으로 안정적 | **GraphRAG 도입** (값을 함) |
| 진입 개체를 먼저 찾아야 함 | 벡터로 seed → 그래프 탐색 (**하이브리드**) |
| 코퍼스가 자주 바뀜 | 재인덱싱 부담 큼 → 증분 갱신 고려 or 벡터 RAG |

**한 줄 판단 기준**: *"연결이 답인 질문이 자주 나오는가"* → 예면 GraphRAG.

### 2.3 도구·구조

**Microsoft GraphRAG**(2024 공개)가 대표 구현. 인덱싱에서 코퍼스에 구조를 미리 새긴다.

```
인덱싱 (한 번, 무겁게)                    쿼리 (질문 크기에 따라)
  문서 → LLM 추출 → KG                       질문 → [지역 vs 전역?]
       → community detection(Leiden)          ├ local:  노드 이웃 + 텍스트
       → 커뮤니티 요약 미리 굽기 ──────────────┤
                                              └ global: 커뮤니티 요약 map-reduce
```

### 2.4 함정·비용

- **인덱싱 비용**: 코퍼스 전체를 LLM으로 추출·요약 → 초기 비용·시간 큼.
- **재인덱싱 부담**: 코퍼스가 자주 바뀌면 반복 비용 커짐(증분 갱신으로 완화).
- **트레이드오프**: 인덱싱 비용을 대가로 다중 홉·전역 질문의 **답변 품질 + 근거 제시(경로)** 능력을 얻음.
- **오버엔지니어링 주의**: 단순 조각 검색·최신성 우선이면 벡터 RAG로 충분. GraphRAG는 그 위에 얹는 보완층.

## 3. 그래프 임베딩·추론

### 3.1 핵심 개념

- **핵심 전환**: 그래프의 노드·관계를 벡터로 옮기면 "읽기"가 "예측"으로 바뀜. 저장되지 *않은* 사실을 추정 가능.
- **node2vec (구조 기반)**: 그래프 위 random walk로 "이웃 문맥" 수집 → word2vec처럼 함께 자주 등장하는 노드가 가까운 벡터. **관계 종류는 무시, 연결 구조만** 봄.
- **TransE (지식 그래프 임베딩)**: 관계를 벡터 공간의 **평행이동**으로. 트리플 (head, relation, tail)에 대해 `h + r ≈ t`. 같은 관계는 어디서 더해도 같은 방향·길이 → 규칙적 배치. (TransR·RotatE·ComplEx가 표현력 확장, 뿌리는 평행이동.)
- **링크 예측(link prediction)**: 임베딩 공간이 규칙적이면 아직 없는 관계를 점수화. TransE라면 `h + r`이 `t`에 얼마나 가까운지로 그럴듯함 측정. **결과는 확정 사실이 아니라 검증할 가설**.
- **다중 홉 추론**: 그래프의 경로·규칙을 따라 새 사실을 명시적으로 도출.
  - **규칙·경로 기반**: "A는 B의 부모, B는 C의 부모 → A는 C의 조부모". OWL 추론(이행성·역관계)이 형식적 뿌리. **경로가 곧 근거 → 설명 가능**.
  - **GNN**: 노드가 이웃 정보를 message passing으로 주고받으며 표현 갱신. 겹을 쌓을수록 먼 이웃까지. 강력하나 **근거 불투명**.

### 3.2 의사결정 규칙

| 목표/조건 | 선택 |
| --- | --- |
| 관계 종류 무관, 구조적 유사 노드 찾기 | **node2vec** |
| 관계 타입까지 담아 링크 예측 | **TransE 계열** (`h+r≈t`) |
| 추천·약물 재창출·사기 연결 발굴 | **링크 예측**(가설 생성 → 검증 후 확정) |
| 설명가능성이 중요(의료·금융) | **규칙·경로 기반 추론** |
| 표현력·성능 우선, 설명 덜 중요 | **GNN / 임베딩** |
| 예측 링크를 그래프에 확정하려 할 때 | 4단계처럼 **실험·검수(휴먼인더루프)** 후 확정 |

**긴장의 축**: 규칙·경로 = 설명가능성↑, 표현력 제한 ↔ GNN·임베딩 = 표현력↑, 블랙박스. 도메인의 설명가능성 요구가 저울을 기울인다.

### 3.3 도구·스니펫

```text
TransE 스코어링:  score(h, r, t) = -‖ h + r − t ‖
  예)  vec(유전자X) + vec(관여) ≈ vec(질환Y)
       vec(약물A)   + vec(치료) ≈ vec(질환Y)

링크 예측:  후보 (h, r, ?) 에 대해 모든 t 후보의 score 상위 순위 →
            "질환 ↔ 약물 A?" 같은 미발견 관계를 가설로 제안
```

### 3.4 함정·비용

- **예측 ≠ 사실**: 링크 예측은 **가설 생성**. 실험·검수로 확인 후 그래프에 확정(휴먼인더루프 원칙).
- **node2vec 한계**: 관계 종류를 구분 못 함 → 타입이 중요한 KG엔 TransE 계열 필요.
- **GNN 설명가능성**: 왜 그 답인지 규칙 기반보다 설명 어려움. 규제 도메인에서 리스크.
- **추론 능력의 통합**: 이 도구들(임베딩·링크 예측·다중 홉)은 에이전트가 스스로 골라 쓰는 밑천이 된다.

## 4. 세 단계를 관통하는 판단 원칙

- **품질을 가르는 것은 추출이 아니라 검증**: LLM이 있어도 스키마 규율·엔티티 해소 숙제는 남고, 환각이라는 새 문제가 더해진다.
- **휴먼인더루프는 전 단계 공통**: 저신뢰·경계 트리플(4단계)도, 예측 링크(6단계)도 사람이 마지막 관문을 지키고 판정을 피드백.
- **보완이지 대체가 아님**: LLM 추출은 전통 파이프라인의 한 상자, GraphRAG는 벡터 RAG의 보완층, 임베딩·추론은 읽기 위에 얹는 예측층.
- **비용은 항상 앞단에 몰림**: LLM 추출(토큰), GraphRAG 인덱싱(추출+요약), 임베딩 학습 — 모두 초기 비용을 치르고 질의·예측 비용을 낮추는 구조.
- **연결이 답인가**를 반복해서 물을 것: 벡터로 충분한지, 그래프가 값을 하는지의 단일 기준.
